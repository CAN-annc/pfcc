## 結論

最該處理的是五個「高」：日期用 UTC 計算（R1）、一次記帳拆成多個交易（R2）、匯入實際上是合併（R3）、寫入失敗被吞掉（R6）、資料沒有要求持久保存（R4）。前四個都會讓資料「看起來正常、實際已錯」，而且偏差會留下來。

v2.31.0 已修 R1、R3。R2 與 R6 完成第一批：寫入鎖、記支出／記收入／轉帳改成單一交易、寫入路徑與必要讀取不再吞錯。其餘寫入路徑列在 R2 底下。

## 系統理解

- **目的**：單人使用的 Local-First PWA，回答「這個月手上的錢可以放心花多少」，用每月規劃把收入分到固定支出、投資、生活費與存錢目標。
- **入口**：`files/index.html`（畫面、導覽、流程、寫入、自動記帳、匯入匯出，約 18,200 行）→ `init()`：開資料庫、密碼鎖、補套用到期的餘額效果、`runAutoConfirm()`、`navigate()`。
- **核心 domain**：`files/calc.js`，純計算函式，沒有依賴 DOM 或資料庫，可以直接測試。
- **資料存取**：`files/db.js`，IndexedDB schema v16、29 個 store；v2.31.0 起有 `runTx` 單一交易工具。帳戶與信用卡的餘額是存下來的欄位，用「讀出 → 加減 → 寫回」更新，不從紀錄重算。
- **外部整合**：`files/api/*.js`（Vercel Edge：匯率、股價、金價、持股分類）只送出市場、代號與幣別；`files/market.js` 呼叫這些 API 並寫回本機。`files/sw.js` 負責離線快取。
- **跨裝置**：只靠手動匯出／匯入 JSON。

## 高與中的細節

### R1 業務日期用 UTC（✅ 已修）

- **涉及**：`calc.js` `currentMonthStr()`；`index.html` 33 處 `new Date().toISOString().slice(0, 10)`，與本地版 `isoDate()` 混用。
- **風險**：UTC+8 每天 00:00–07:59 的 UTC 日期是前一天；每月 1 日早上 8 點前仍是上個月。
- **情境**：11/1 早上 7:30，計畫頁顯示「10 月還沒規劃」。每日快照寫到前一天。
- **改善**：`calc.js` 的 `localDate()`／`localMonth()` 作為唯一入口；備份檔名與時間戳記仍用 ISO。
- **成本與取捨**：低。以前已經錯一天的紀錄無法自動判斷。
- **驗證**：`tests/calc.test.mjs` 的 T1–T7、`tests/e2e_writes.py` 的 E16（v2.30.0 失敗，v2.31.0 通過）。

### R2 一次操作拆成多個交易（🟡 部分）

- **涉及**：記支出、記收入、轉帳、刪除、繳卡費、賣出、各種確認本期，共 28 處改餘額，每個 `putOne()` 都是獨立交易。
- **風險**：中途失敗時紀錄存了、餘額沒扣；同時寫入時後寫的蓋掉先寫的。餘額不從紀錄重算，偏差會永久留下。
- **情境**：自動記帳正在記房租，同時記一筆午餐。兩邊都讀到 30,000，最後餘額 29,880，房租那筆在紀錄裡卻沒有扣錢。
- **改善**：（a）寫入鎖（Web Locks）讓寫入排隊；（b）一次業務操作的所有 store 放進同一個交易，這才提供原子性，鎖不能取代它；（c）資料健檢加餘額對帳。
- **成本與取捨**：（a）低；（b）中，逐個操作改；（c）中，需要可信的起點。不建議改成餘額完全由紀錄推導。
- **已完成（v2.31.0）**：（a）；（b）的記支出、記收入、轉帳（含帳戶移轉、扣款前補足、發薪後分流、定期轉帳確認本期）。驗證：E1–E11（E2、E3、E4 在 v2.30.0 失敗）。
- **尚未遷移的寫入路徑**：

| 路徑 | 會動到的 store | 寫入鎖 |
| --- | --- | --- |
| 刪除收支 `deleteTxnRecord` | 餘額、保單、確認狀態、應收款與股數、紀錄本身（四段各自交易） | 有 |
| 分期確認本期 `commitInstPeriod` | 支出已是單一交易；`installments` 已繳期數另外寫 | 自動記帳時有 |

| 信用卡繳款與撤銷 `ccPaySave`／`undoCcPayment` | `accounts`、`credit_cards`、`balance_adjustments` | 無 |
| 持倉賣出 `saveStockSale` | `holdings`、`income_txns`、`accounts` | 無 |
| 定存新增與到期 `depositModalSave`／`depositMatureConfirm` | `accounts`、`time_deposits`、`transfer_logs`、收入 | 無 |
| 轉帳頁刪除移轉紀錄 | `accounts`、`transfer_logs`、`recurring_transfers` | 無 |

| 未來日期到期補套用 `applyPendingBalanceEffects` | `accounts`、`credit_cards`、紀錄 | 無 |

- **已知限制**：自動記帳執行期間，同一個視窗裡的其他寫入不等鎖（巢狀判斷是視窗層級）；iOS 15.4 以前沒有 Web Locks，鎖只在同一個視窗裡排隊。

### R3 匯入實際是合併（✅ 已修）

- **涉及**：匯入逐 store `putMany()`、不清空，每個 store `.catch(() => {})`，最後一律顯示成功。
- **風險**：目標裝置多出的紀錄留著，刪掉的紀錄復活；匯入只成功一半，使用者卻看到成功。
- **情境**：換新手機先試記幾筆再匯入，試記的紀錄和備份混在一起，餘額卻是備份的值。
- **改善**：驗證格式 → 自動留還原點（`pfcc_restore`）→ 單一交易涵蓋 29 個 store，先清空再寫入 → 失敗整批放棄並說明原因 → 重新載入。匯出時任何 store 讀不到就不產生備份。
- **成本與取捨**：低。還原點只留一份，而且跟資料在同一個瀏覽器。
- **驗證**：E12–E15（E12 在 v2.30.0 失敗）；設定頁的匯入流程用 UI 實際操作過。

### R6 寫入失敗被吞掉（🟡 部分）

- **涉及**：202 處 `.catch(() => [])`、33 處 `.catch(() => {})`；原本沒有 `unhandledrejection`、`onblocked`、`onversionchange`。
- **風險**：寫入路徑（高）失敗卻顯示成功；「先讀既有紀錄、讀不到當成沒有、再新增一筆」會產生重複。顯示路徑（中）讀取失敗時顯示 0。
- **情境**：舊分頁擋住資料庫升級，首頁顯示總資產 0；使用者匯入舊備份，問題更難收拾。
- **改善**：寫入路徑不吞錯並明確顯示「沒有存到」；本機事件紀錄；`unhandledrejection` 提示；資料庫升級事件提示重新整理。
- **已完成（v2.31.0）**：上面全部，範圍限於寫入路徑與必要讀取：四個衍生紀錄同步函式、`limited_income` 讀出再寫回的四處、匯出備份、每月規劃確認、三個交易操作。驗證：E4。
- **尚未**：顯示用的 `catch`（目前掃描 `index.html` 有 226 處符合）；尚未遷移的寫入路徑（見 R2）內的 `catch`。

### R4 沒有要求持久保存（⬜）

- **風險**：瀏覽器空間不足時可以清除網站資料；Safari 對沒有加到主畫面的網站，7 天沒使用會清除。
- **改善**：呼叫 `navigator.storage.persist()`，但它只是請求，瀏覽器可以拒絕，不能當成資料保護策略。真正的保護是「超過 30 天沒匯出就提醒」，加上可驗證的還原（R3 的還原點）。
- **成本**：低。

### R5 自動記帳的多視窗防重複（🟡）

- **現況**：整次 `runAutoConfirm` 已在寫入鎖裡，另一個視窗會等這邊做完再讀已處理清單。完整解法見 R11。

### R7 報價代理任何人都能呼叫（⬜）

- **涉及**：四個 API 都回 `Access-Control-Allow-Origin: *`；`vercel.json` 對 `/api/*` 設 `no-store`；`quote.js` 的台股代號沒有格式驗證。
- **風險**：拿掉 CORS 只能擋住別的網站在瀏覽器裡讀回應，擋不住 curl 或伺服器直接呼叫，Finnhub 額度可能被耗盡。
- **改善**：代號格式驗證（套用 `classify.js` 的正規式）、回應加 `s-maxage` 快取、依 IP 限流、拿掉 `*`；必要時加應用層限制。
- **成本與取捨**：低到中。報價最多晚 60 秒。

### R8 動態文字未跳脫（⬜）

- **涉及**：`innerHTML` 323 處；`${x.name}` 這類沒有 `escHtml()` 的插值約 140 處；沒有 CSP。
- **風險**：惡意字串可以從任何入口進到資料庫（輸入欄位、匯入、未來的同步），只要有一處輸出沒跳脫，就能在 App 網域執行並讀出全部資料。
- **改善**：在輸出端預設用 `textContent` 或一致的 `escHtml()`；匯入時的 schema 驗證當作額外一道防線；CSP 先用 Report-Only。
- **成本**：中；CSP 另計。

### R9 service worker 版本錯開（⬜）

- **涉及**：同源檔案一律先給快取、背景逐檔更新；安裝時無條件 `skipWaiting()`，但 `register-sw.js` 又寫著要等使用者按「立即更新」。
- **風險**：新的 `index.html` 匯入舊 `calc.js` 沒有的函式，整個模組載入失敗，畫面一片白，離線時無法自救。
- **改善**：App 檔案只從目前版本的快取讀（安裝時整組快取），或改成先上網、3 秒逾時才用快取；兩種更新提示流程擇一保留。
- **成本**：低。

### R10 寫入邏輯散在畫面（🟡）

- **改善**：先在原地建立少數交易操作（已有 `recordExpense`、`recordIncome`、`recordTransfer`、`importBackupData`），把 R2 表中的路徑逐一改成呼叫它們；穩定後再決定要不要搬到獨立檔案。

### R11 自動記帳防重複清單會被截斷（⬜）

- **涉及**：`auto_confirm_done` 寫回時 `slice(-400)`，掃描範圍從開啟自動記帳那天起只增不減；分期只比對最後一期的月份。
- **情境**：每月約 15 個排程，大約兩年後清單滿了，兩年前的某一期分期被再記一次。
- **改善**：每一期一個穩定的冪等鍵（`類型:排程 id:排定日期`），放在獨立 store、永不截斷，跟紀錄寫在同一個交易；可以從既有紀錄的確認欄位重建。不要縮短掃描期間，否則很久沒開 App 時會漏記。
- **成本**：低到中（DB 版本 +1，加一次遷移）。

### R12 沒有自動測試（🟡）

- **已完成**：`npm --prefix files test`（7 個時區單元測試）；`python tests/e2e_writes.py`（17 個瀏覽器測試：寫入、交易、多分頁、匯入、時區）。
- **尚未**：可自由運用、可撐多久、成長拆解、可規劃收入等計算；尚未遷移的寫入路徑；沒有接 CI。
- **規則**：每修一個問題就加一個能重現它的測試，並在舊版跑一次證明它會失敗。

### R13 「進來」有三種算法（⬜）

- **涉及**：月底回顧排除股利與已實現損益；報表「錢的去向」不排除；每月計畫另外排除獎金。
- **改善**：不強制統一成一個數字，而是分別命名為「可規劃收入」「總流入」「投資收益」，各用一個 `calc.js` 函式集中定義排除條件，畫面標籤跟著改，需要時加 ⓘ 說明。v2.30.0 的「沒有去處」用的是可規劃收入。
- **成本**：低。

## 建議處理順序

1. ✅ 本地日期單一入口（R1）。
2. 🟡 寫入鎖，再把各操作逐一改成單一交易（R2、R5、R10）。下一批：刪除收支、信用卡繳款、分期確認、轉帳頁刪除移轉紀錄。
3. ✅ 匯入全量取代、可回復、失敗就明確失敗（R3）。
4. 🟡 寫入路徑禁止吞錯（R6）。
5. 🟡 每一項修正都附回歸測試（R12）。
6. ⬜ 接著做：輸出跳脫（R8）、API 防濫用（R7）、service worker 整組更新（R9）、冪等鍵（R11）、收入命名（R13）、持久保存與備份提醒（R4）、清掉殘留（R14）。

R10 的檔案整理、R2(c) 餘額對帳、R16 精簡註解、R15 加密備份放在這六步之後。
